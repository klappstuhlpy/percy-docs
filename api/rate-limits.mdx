---
title: "Rate limits"
description: "60 requests per minute per token with a burst of 20, and how to read the rate-limit headers."
---

Each token gets **60 requests per minute**, with a **burst of 20**. You can send up to 20 requests at once. After that, the allowance refills steadily.

Requests without a valid token are limited per IP address instead, at 30 per minute with a burst of 20.

## Headers

Every response from a token request includes:

| Header | Meaning |
|---|---|
| `X-RateLimit-Limit` | The size of the bucket |
| `X-RateLimit-Remaining` | Requests you can still send right now |
| `X-RateLimit-Reset` | Seconds until the bucket is full again |

## When you go over

Percy answers `429` with the code `rate_limited` and a `Retry-After` header. The value is the number of seconds to wait.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 3
X-RateLimit-Remaining: 0

{"error":{"code":"rate_limited","message":"Too many requests. Retry in 3 s."}}
```

## Be a good client

- Wait `Retry-After` seconds, then retry.
- Watch `X-RateLimit-Remaining` and slow down before it hits 0.
- Use `limit=100` on list endpoints instead of many small pages.
- Cache values that change rarely, such as the shop.
- Send an [Idempotency-Key](/api/idempotency) on writes, so a retry after `429` or a timeout is safe.
